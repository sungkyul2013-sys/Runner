# APEX_SIM 착수 보고서 (§2.1 · §26)

> 상태: **승인 대기**. 승인 전에는 M0 코드를 쓰지 않는다.
> 함께 보는 문서: [ARCHITECTURE.md](ARCHITECTURE.md) (④ 아키텍처 초안) · [ROADMAP.md](ROADMAP.md) (⑤ 마일스톤 계획) · [REQUIREMENTS.md](REQUIREMENTS.md) (§2.3 추적표)

## 0. 요약

- **제안: 스펙 §3의 "웹 버전" 대안으로 진행한다.** 이 개발 환경(리눅스 클라우드 컨테이너, GPU·Windows 없음)에서는 UE5를 설치·빌드·실행할 수 없다. UE5를 고르면 매 마일스톤의 "실행 가능한 빌드 + 스크린샷"(§2.2)을 내가 직접 확인하지 못하고, 확인하지 않은 채 완료로 보고하면 §1.8 위반이 된다. 반면 웹 버전은 이 환경에서 끝까지 빌드·테스트·스크린샷 검증이 가능하다(§1 실측 참고).
- 물리 코어 `SoftBodyCore`는 스펙대로 **엔진 독립 C++20**이다. 네이티브(테스트·CLI·벤치)와 WASM(SIMD + 멀티스레드) 두 가지로 빌드한다. 나중에 UE5로 옮기더라도 코어는 그대로 쓰고 표현 계층만 바꾸면 된다.
- 결정이 필요한 질문은 **7개**(§2)다. **Q1(기술 스택)과 Q2(저장소 위치)만 정해지면 M0를 시작할 수 있고**, 나머지는 해당 마일스톤 전까지 정하면 된다.
- 스펙 안의 불명확·상충 항목 10개(§3)와 가정 13개(§4)는 제안안대로 진행한다. 이견이 있으면 알려 달라.

## 1. 개발 환경 점검 결과 (실측, 2026-09-23)

| 항목 | 결과 | 영향 |
|---|---|---|
| 하드웨어 | Intel Xeon 2.8 GHz 4 vCPU, RAM 15 GB, **GPU 없음** | 렌더링 성능은 여기서 측정 불가 → 사용자 PC에서 벤치 페이지 실행 필요 |
| C++ 툴체인 | g++ 13.3, clang 18.1, CMake 3.28, Ninja | C++20 코어 네이티브 빌드·테스트 가능 |
| WASM 툴체인 | Emscripten 6.0.10 설치·동작 확인 (`-msimd128 -pthread`) | 코어 WASM 빌드 가능 |
| 브라우저 | 헤드리스 Chromium: **WebGL2 ✔, WebGPU ✔** (`--enable-unsafe-webgpu`, SwiftShader CPU 래스터라이저), COOP/COEP 설정 시 `SharedArrayBuffer`·`crossOriginIsolated` ✔ | 렌더링 결과 스크린샷·E2E 테스트 가능(속도는 느림) |
| npm 패키지 | three 0.186(MIT), preact(MIT), @preact/signals(MIT), uplot(MIT), pretendard(OFL), @fontsource/inter·jetbrains-mono(OFL) 확인 | 가정 A7 |
| Node.js | v22 (WASM 스레드 지원) | 코어 WASM 테스트를 Node에서 헤드리스 실행 가능 |
| 네트워크 허용 | npm 레지스트리 ✔, GitHub(git clone) ✔, Emscripten 배포 저장소 ✔ | 의존성 설치 가능 |
| 네트워크 차단 | **polyhaven.com, ambientcg.com, unrealengine.com** (조직 네트워크 정책, HTTP 403) | CC0 에셋 다운로드 불가 → Q5 |
| Git LFS | 미설치 | 대용량 바이너리 에셋이 생길 때(M4) 설치 |

**빔 처리량 마이크로벤치마크** ([bench/feasibility/beam_throughput.cpp](bench/feasibility/beam_throughput.cpp)).
조건: 차량 1대 = 노드 1,500개 / 빔 15,000개, dt = 0.5 ms, 빔 힘 계산 + symplectic Euler만 측정. 스칼라 코드이며 수작업 SIMD는 적용하지 않았다.

| 빌드 | 1스레드 빔 갱신/s | 차량 1대 1스텝 빔 비용 | 4스레드·4대 합계 |
|---|---|---|---|
| 네이티브 (`-O3 -march=native`) | 110–118 M | 0.13 ms | 415–465 M/s |
| WASM (SIMD128 + pthreads, Node 22) | 70–73 M | 0.21 ms | 316–338 M/s |

→ WASM은 네이티브의 약 **62–65%** 속도다. 실시간(RTF 1.0)이 되려면 스텝당 0.5 ms 안에 끝나야 하는데, 빔 계산만으로 0.21 ms가 든다. 충돌·타이어·파워트레인까지 더하면 차량 1대당 코어 약 1개가 필요하다고 추정한다(수작업 SIMD로 줄일 여지는 있음). 이 수치를 근거로 Q3을 묻는다.

## 2. 질문 ① — 결정이 필요한 항목

### Q1. 기술 스택 (§3) — M0 착수에 필요

| 선택지 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 웹 버전 (추천)** | C++20 코어 → WASM(SIMD + pthreads) / Three.js WebGPU 렌더러 / TypeScript + Vite | 이 환경에서 빌드·테스트·스크린샷까지 전부 직접 검증 가능. 설치 없이 브라우저로 실행하고 링크로 공유 가능. 현재 저장소 스택(Vite + TS + Three.js)과 일치 | Lumen·Nanite·DLSS 같은 UE5 기능이 없어 그래픽 상한이 낮다. 휠 포스피드백(FFB)은 별도 해결 필요(Q4) |
| B. UE5 + C++ (스펙 기본값) | 스펙 그대로 | 그래픽 상한이 가장 높다 | UE5 부분은 여기서 빌드·실행·확인 불가. 사용자가 Windows에서 빌드하고 결과를 보내 주는 왕복이 매번 필요 → §2.2 완료 조건을 내가 충족할 수 없다 |
| C. 코어 먼저, 엔진은 M3 전에 결정 | M0–M2를 물리 코어 + 웹 디버그 뷰어로 진행한 뒤 결정 | 결정을 미룰 수 있다 | 디버그 뷰어는 결국 웹으로 만들게 되어 사실상 A와 같다 |

**추천 근거:** A를 골라도 코어는 엔진 독립이라 나중에 UE5 이식 경로가 그대로 남는다. 스펙 §3이 웹 대안의 구성 요소(WASM SIMD + 멀티스레드, Three.js WebGPU)를 명시하고 있어 스펙에서 벗어나지 않는다.

### Q3. 웹 버전의 성능 목표 (§21.7, §23.3) — M2 전까지

스펙 목표는 "권장 사양(8코어, RTX 4070급)에서 고해상도 소프트바디 차량 10대 이상 동시 RTF 1.0"이다. §1 실측으로 보면 웹에서 가능은 하지만 여유가 없다.

| 선택지 | 내용 |
|---|---|
| **A. 스펙 목표를 유지하고 M2 실측 후 재논의 (추천)** | 수작업 SIMD와 물리 LOD로 목표를 추구한다. M2의 10대 충돌 벤치 결과가 미달이면 수치를 그대로 보고하고 B안으로 조정할지 다시 묻는다 |
| B. 지금 웹용 목표로 낮춤 | 풀해상도 차량 6대 RTF 1.0. 10대 충돌 씬은 NPC 차량을 중해상도로 돌리거나, 슬로다운(RTF 표시)을 허용한다 |

함께 확인할 것: 이 컨테이너에는 GPU가 없어서 **렌더링 fps(1440p 60 fps 등)는 사용자 PC에서만 측정할 수 있다.** M0부터 벤치 페이지가 결과를 JSON으로 내보내게 만들 테니, 마일스톤마다 실행해서 결과를 공유해 줄 수 있는지 알려 달라. 사용하는 PC의 CPU·GPU 사양도 알려 주면 좋다.

### Q5. 무료 에셋 사이트 접근 (§2.6) — M4 전까지

§2.6이 지정한 CC0 에셋 출처인 Poly Haven과 ambientCG를 이 환경의 네트워크 정책이 차단하고 있다.

- **A (추천):** 세션 제목 표시줄의 클라우드 환경 메뉴 → Edit → Network access에서 `polyhaven.com`, `api.polyhaven.com`, `dl.polyhaven.org`, `ambientcg.com`을 허용 도메인에 추가한다(또는 더 넓은 접근 수준을 선택한다). 그동안에는 절차적 생성으로 진행한다.
- **B:** 계속 차단된 상태로 절차적 생성 + `TEMP_` 교체 슬롯만 사용한다(§2.6 ①·③). 에셋은 나중에 사용자가 넣는다.

## 3. 스펙 해석상 불명확·상충 항목과 처리 제안 (① 계속)

이견이 없으면 아래 제안대로 진행한다.

| # | 조항 | 문제 | 제안 |
|---|---|---|---|
| C1 | §4.2 임계 시간 간격 | `dt < 2√(m_r/k)`는 감쇠가 없는 단일 빔 조건이다. 감쇠가 크거나 한 노드에 빔이 여러 개 모이면 이 조건만으로 안전하지 않다 | 검사기가 두 조건을 모두 본다. ① 빔별 감쇠 보정: `dt < (2/ω)(√(1+ζ²) − ζ)`, `ω = √(k/m_r)`, `ζ = c / (2√(k·m_r))`. ② 노드별 Gershgorin 상한: `dt < √(2·m_i / Σ_j k_ij)`. 기본 안전계수 0.8(데이터로 조정) |
| C2 | §5.2 · §23.1 "관통 0" | 노드↔삼각형 CCD만으로는 두 패널의 모서리끼리 교차하는 경우(어느 노드도 면을 넘지 않음)를 잡지 못한다 | "관통"을 이렇게 정의한다. ① 정적 월드: 스텝이 끝났을 때 충돌 노드가 정적 삼각형 뒤쪽(부호 거리 < −노드 반경)에 있으면 1회 ② 차↔차: ①과 같은 기준에 더해, 충돌 삼각형 모서리↔모서리 교차 검사 결과. 둘 다 0회를 합격 기준으로 한다 |
| C3 | §5.3 · §23.1 에너지 수지 | 식에 빔 탄성 위치에너지, 중력 위치에너지 변화, 엔진·브레이크 입력 일, 적분기 수치 오차가 빠져 있다 | 수지 = ΔKE + ΔPE_탄성 + ΔPE_중력 + 소성 흡수 + 감쇠 손실 + 마찰 손실 − 외부 입력 일. 수치 오차는 따로 표시한다. 64 km/h 벽 충돌 테스트는 엔진·브레이크를 끈 상태로 5% 기준을 적용한다 (초기 KE = ½·1500·17.78² = 237.0 kJ, 스펙 값과 일치 확인) |
| C4 | §21.3 결정론 범위 | "같은 결과"가 어디까지인지(스레드 수, 플랫폼) 명시되지 않았다 | ① 같은 WASM 바이너리는 브라우저·OS·스레드 수와 무관하게 비트 단위로 일치 ② 네이티브와 WASM 간 비트 일치도 목표로 한다. 이를 위해 FMA 축약 금지, fast-math 금지, 비정규수 유지, 초월함수(sin·cos·exp 등)는 libm 대신 자체 구현을 쓴다 |
| C5 | §3 Chaos 파편 | 웹 버전에는 Chaos가 없다 | 차량과 상호작용하지 않는 작은 파편은 자체 경량 GPU 파티클로 처리한다. 차량에 닿는 모든 물체는 여전히 코어가 담당한다 |
| C6 | §11.4 cm 단위 미세 요철 | 물리에 반영된다는 것과 "텍스처가 아니다"(§1.2)의 구현 방식이 명시되지 않았다 | 미세 요철은 결정론적 함수(노이즈 + 재질별 파라미터)로 정의한다. 물리는 접촉점에서, 렌더러는 변위 셰이더에서 같은 함수를 샘플링해 보이는 것과 물리가 일치하게 한다. 방지턱·연석·포트홀은 실제 메시 형상으로 만든다 |
| C7 | §23.2 "차량 데이터 목표 ±5%" | 목표 데이터를 어디에 두는지 정해지지 않았다 | 차량 JSON에 `targets` 블록(0-100 시간, 제동거리, 최고속도, Cd·A, Crr 등)을 두고 자동 시험이 이 값과 비교한다 |
| C8 | §21.7 "SSD 기준 맵 로딩 30초" | 웹은 네트워크 다운로드가 끼어든다 | 로컬 서버 또는 브라우저 캐시 상태에서 측정하고, 첫 다운로드 시간은 별도로 기록한다 |
| C9 | §15.2 되감기 30~60초 | 메모리 예산이 정해지지 않았다 | 0.5초마다 키프레임 스냅샷을 찍고 입력 로그를 재시뮬레이션한다. 풀해상도 차량 1대의 키프레임은 약 0.1 MB이므로 60초 × 차량 10대 ≈ 130 MB 상한이다(설정 가능) |
| C10 | §3 락프리 트리플 버퍼 (웹) | 브라우저에서 스레드 간 공유 메모리를 쓰려면 `SharedArrayBuffer`가 필요하고, 이는 COOP/COEP 헤더를 요구한다 | 배포처가 헤더를 지원해야 한다 → 가정 A3 |

## 4. 가정 ②

| # | 가정 |
|---|---|
| A1 | 코드네임 `APEX_SIM`, 폴더 `apex-sim/`. 문서와 보고는 한국어, 코드 식별자는 영어(§2.9) |
| A2 | 목표 브라우저는 데스크톱 Chromium 계열(Chrome·Edge) WebGPU 우선이다. Firefox·Safari는 최선 노력으로 지원한다. WebGPU가 없으면 WebGL2 백엔드로 기능을 줄여 동작한다 |
| A3 | 배포는 COOP/COEP 헤더를 설정할 수 있는 정적 호스팅(Cloudflare Pages·Netlify의 `_headers`)을 쓴다. GitHub Pages라면 `coi-serviceworker` 방식을 쓴다. 러너 게임의 `play.html` 단일 파일 방식은 `file://`에서 WASM 스레드가 동작하지 않아 쓰지 않는다 |
| A4 | 좌표 정밀도: 차량마다 double 원점을 두고 노드는 float32 로컬 좌표로 저장한다. 원점에서 10 km 떨어진 곳의 float32 해상도는 약 1 mm로, 0.5 ms 스텝의 미세 이동을 표현하지 못하기 때문이다. 정적 월드 셀도 셀마다 double 원점을 둔다 |
| A5 | 적분기는 symplectic(반암시적) Euler를 쓴다. [선택] XPBD 실험은 M2 이후에 한다 |
| A6 | 테스트: 코어는 Catch2 v3(네이티브 + WASM/Node 양쪽 실행), 웹은 Vitest, E2E·스크린샷은 Playwright + 헤드리스 Chromium |
| A7 | 서드파티는 허용 라이선스만 쓴다(MIT, BSD, Apache-2.0, BSL-1.0, Zlib, OFL, CC0). 초기 후보: three(MIT), preact(MIT), uPlot(MIT), Catch2(BSL-1.0), yyjson(MIT), Pretendard·Inter·JetBrains Mono(OFL, npm 레지스트리에서 확인). 모두 CREDITS.md에 기록한다 |
| A8 | 과속방지턱 치수는 스펙 §11.3 본문의 값을 기준으로 한다(지침 원문은 보지 못했다). 모든 치수는 데이터 파일에서 조정할 수 있다 |
| A9 | 브랜드·차명·상호·타이어 레터링은 전부 가상으로 만든다(§1.7) |
| A10 | 물리 성능은 이 컨테이너(4 vCPU)와 사용자 PC에서, 렌더링 성능은 사용자 PC에서만 측정한다(Q3) |
| A11 | 대용량 에셋은 가능한 한 빌드 타임에 생성하고 커밋하지 않는다. 커밋이 필요해지면 Git LFS를 설정한다 |
| A12 | 모바일 빌드와 멀티플레이는 스펙대로 각각 M10 [선택], 아키텍처 대비만 한다 |
| A13 | 기존 Sunset Runner 게임 파일은 수정하지 않는다 |
